상속 관계 매핑 : 객체의 상속 구조와 DB의 슈퍼 타입과 서브 타입 관계를 매핑(DB에는 참고로 상속이라는 개념이 없다)
-> 참고로 실제로 DB에 슈퍼 타입과 서브 타입이라는 타입이 존재하는 것이 아니다. 어디까지나 논리 모델 속에서의 개념이다.

슈퍼타입-서브타입 논리모델을 실제 물리 모델로 변환하는 방법은 크게 3가지
1. 각각 테이블로 변환하여, 조인을 이용
2. 통합 테이블로 변환하여 단일 테이블 이용
3. 서브 타입 테이블로 변환하여 구현 클래스마다 테이블 생성 전략
-> 애플리케이션 코드의 객체 상속 관계를 위 3가지 중 어떤 전략으로 DB를 물리적으로 설계를 하여도, JPA를 사용하여 객체의 상속관계와 매핑을 시킬 수가 있는 것이 핵심이다.
참고로 JPA는 객체의 상속 관계 매핑을 하지 않으면 디폴트로 전략2를 채택하여 단일 테이블을 만든다.


・@Inheritance(strategy = InheritanceType.JOINED) : 전략 1,2,3시 사용하는 매핑 애노테이션이며, 부모 객체에서 사용하는 매핑이다.
이 애노테이션의 옵션 "JOINED" 설정을 하게 되면 JPA는 그 부모를 상속 받은 모든 객체 엔티티에 대해 각각 테이블을 생성하며, 조인을 통하여 객체의 상속 관계를 전략 1 방법으로 DB 물리 설계를 한다.
em.find 시에도 조인 SQL을 통해 상속 관계 객체를 조회한다.
※DTYPE : JPA은 @DiscrimnatorColumn이 사용된 경우, DTYPE이라는 컬럼을 자동으로 생성을 한다. DTYPE 컬럼을 만드는 이유는 "부모 테이블에서 해당 레코드가 어떤 자식 테이블에 대한 레코드인지 식별하기 위함"
-> ex) 부모 테이블(ITEM 테이블) : DTYPE = "MOVIE"인 레코드가 있으면 그 레코드는 MOVIE 테이블에 대한 데이터라고 식별할 수가 있다.
@DiscriminatorColumn을 부모 객체에서 사용하여 DTYPE이라는 컬럼명 대신 원하는 컬럼명을 지정 가능. 그러나 김영한 왈 관례적으로 DTYPE을 사용하는 것이 좋다고 한다.
@DiscriminatorValues는 자식 객체에서 사용하는 것인데, 부모 테이블의 컬럼인 DTYPE에 들어가는 자식 객체 식별자를 지정해줄 수가 있다.
-> ex) @DiscriminatorValue("MOVIE_SUB")라고 Moview 객체에 적게 되면, Moview 객체를 INSERT 시, DTYPE 컬럼에는 "MOVIE_SUB"가 들어 가게 된다.
만약에 아무런 설정을 하지 않으면 JPA는 디폴트로 자식 객체의 엔티티 명을 DTYPE에 넣는다.

이 방법의 특징
1. 각 테이블마다 INSERT/UPDATE문이 실행되며, 조회시 조인이 필요

・@Inheritance(strategy = InheritanceType.SINGLE_TABLE) : 전략 2를 구현!!!

이 방법의 특징
1. 아무래도 단일 테이블이다 보니, INSERT/UPDATE문도 1번만 실행되면 , 조회 시 조인도 필요가 없다.
2. @DisciminatorColumn을 생략해도 JPA가 반드시 DTYPE을 자동 생성한다.
-> 전략 1의 경우 부모 테이블의 레코드 데이터가 어떤 자식 테이블의 데이터인지 식별하기 위해서 굳이 DTYPE이 없어도 자식 테이블들이 가지고 있는 부모 테이블의 FK를 가지고 모든 자식 테이블에 대해 조회를 하여서
식별이 가능하다. 그러나 단일 테이블의 경우 1개의 테이블안에 부모 객체 데이터와 자식 객체 데이터가 담기는데 DTYPE이 없으면 단일 테이블의 레코드가 대체 어떤 자식 [객체]의 데이터인지 식별할 방법이 없기 때문에
반드시 DTYPE 컬럼을 생성한다.

・@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS) : 전략 3시 사용
-> 주의점으로 반드시 부모 클래스에 abstract를 붙여 줘야 한다.
왜냐하면 abstract 생략 시에는 부모 객체 단독으로 엔티티를 만들 수 있게 되버린다.
그러나 전략 3의 방법은 오직 자식 엔티티만을 테이블로 만들기 때문에 그것을 JPA에게 알려 주기 위하여
abstract를 붙여 준다.
참고로 TABLE_PER_CLASS 모드에서는 @DiscriminatorColumn으로 DTYPE을 만들 필요가 없다.
왜냐하면 DTYPE의 목적은 해당 레코드가 어떤 테이블의 데이터인지를 식별하기 위함인데 TABEL_PER_CLASS
에서는 자식 테이블이 각각 만들어 지기 때문에 DTYPE이 없어도 해당 레코드가 어떤 테이블의 레코드인지 바로 식별 가능하다.


전략3의 애플리케이션에서 부모 타입으로 find시 망하는 전략이다
-> 만약 entityManger.find(Item.class, item.getId)로 조회했을 떄
전략1의 경우는 부모 테이블의 ITEM_ID를 가지고 DTYPE을 가지고 자식 테이블을 특정하여 FK로 조인을 하여 바로 ITEM 객체의 자식 타입을
1개의 조인 쿼리로 들고 올 수가 있다.
전략2의 경우의 단일 테이블이고 DTYPE을 아니깐 이건 조인도 사용하지 않고 1개의 쿼리문으로 바로 들고 올 수가 있다.
그러나 전략 3의 경우는 애초에 부모 테이블이라는 것도 존재하지 않고 DTYPE이라는 것도 없으니깐
item.getId()에 해당하는 자식 테이블을 식별하기 위해서는 모든 자식 테이블에 item.getId()가 있는지 전부 조회를 해야만 한다.
이떄 부하가 많이 걸린다.


전략1,2,3의 장단점
전략1
장점 :
1. 테이블 정규화에 인한 저장 공간 효율화
2. 【외래 키 참조 무결성 제약조건】 활용 가능
-> 테이블 정교화가 잘 돼 있으니, 만약 Order 테이블에서 자식 테이블을 참조하고 싶을 때에는 Order 테이블에 ITEM_ID라는 FK를 가지게 하여
슈퍼 타입인 ITEM 테이블과 DTYPE만을 보고 Order 테이블에서 자기가 어떤 물건을 주문하였는지 알고 싶을 떄 식별이 가능하다.

단점 :
1. INSERT/UPDATE문이 2번씩 나간다.
2. JOIN으로 인한 성능 이슈
-> 김영한 왈 : 자기는 이게 크게 단점이라고 생각 안한다. INSERT/UPDATE문이 2번 나가는 것은 성능에 그닥 크게 영향을 안 미치고
조인도 설계만 잘 해놓으면 얼마든 최적화가 가능하다고 한다. 그리고 조인 방식이 객체의 연관 관계랑도 비슷하여 뭔가 객체스럽고...

3. 쿼리문이 복잡해짐
-> 조회/등록/변경 시 아무래도 단일 테이블 등에 비해서는 상대적으로 복잡해 진다.

전략 2
장점 :
1. 조인이 필요없으므로 일반적으로 조회 성능이 빠름
2. 전략 1에 비해 상대적으로 조회 쿼리가 단순함

단점 :
1. 자식 엔티티가 매핑한 컬럼에 NULL을 허용해야만 한다.(치명적인 단점)
-> 만약 ALBUM을 주문한 경우 단일 테이블에 NAME,PRICE,ALBUM 컬럼 이외의 DIRECTOR,ACTOR, AUTHOR 등의
ALBUM 이외의 자식 테이블 관련 컬럼은 모두 NULL을 허용해야만 한다. 그래서 만약 ALBUM 객체를 DB에 저장하게 되면
다른 컬럼에는 반드시 null을 넣어야 한다.
null을 허용하므로 생기는 치명적인 단점은 저장 공간을 낭비한다는 것이 핵심 단점이라기 보다는 각 자식 엔티티에 필요한 제약 조건을
DB에서 걸기 어려워 진다는 것이다. 예를 들어 Album 엔티티에서 반드시 artist 부분이 NOT NULL이여야 하는 제약조건을 건다고 하자.
이떄 만약 MOview 자식 엔티티가 저장이 되면 필연적으로 artist 칼럼 부분이 null이여야 하므로 Album 엔티티에는 제약 조건을 걸지 못한다.
그래서 "데이터 무결성"을 꺠뜨리게 된다

2. 단일 테이블에 모든 것을 저장하기 떄문에 테이블이 커질 수 있기에 "상황에 따라서는" 조회 성능이
오히려 느려 질 수가 있다.
-> 일반적으로는 이 전략2가 조회 성능이 더 빠르다.

전략 3(절대 쓰면 안 되는 전략임, 전략3은 DBA와 개발자 둘다 추천하지 않는 전략임)
장점 :
1. 서브 타입을 명확히 구분해서 처리할 떄는 효과적
-> 객체 타입을 구분해서 INSERT/UPDATE문 날릴 떄에는 효과적
왜냐하면 전략1과는 달리 서브 타입에 쿼리문을 날리고 싶다면 전략1과 달리 단 1개의 INSERT/UPDATE문만 날리면 된다.

2. NOT NULL 제약 조건 사용 가능
-> 자식 객체마다 자식 테이블이 생성이되므로 null 처리가 필요 없다.그래서 제약 조건 거는 게 가능

단점 :
1. 여러 자식 테이블을 함께 조회할 떄 성능이 느림(UNION ALL SQL)
-> 이 단점의 핵심은 딱 1개이다. 바로 "애플리케이션 코드에서 부모 객체인 ITEM으로 조회 시 성능이 매우 느려진다는 것".
만약 영업이 다 끝나고 하루 동안의 매출을 정산하는 쿼리문을 작성해야 한다고 가정하자. 우리는 그를 위해서 NAME, PRICE 컬럼만 조회하면 된다.
그러나 DB에는 ITEM 부모 테이블이 없으므로, 모든 자식 테이블을 아래의 같이 UNION ALL SQL문을 작성할 수 밖에 없다.
ex)
SELECT NAME,PRICE FROM ALBUM
UNION ALL
SELECT NAME,PRICE FROM MOVIE
UNION ALL
SELECT NAME,PRICE FROM BOOK
UNION ALL
.....
-> 자식 테이블이 3,4개일 떄는 문제가 안되지만 만약에 자식 테이블이 20개 정도로 확장된다면?? 매우 느려진다.
전략1의 경우는 애플리케이션 코드에서 부모 타입인 ITEM객체로 해당 위 목적을 위해 조회를 할 경우 FK와 DTYPE으로 최적화가 가능하며, 전략 2의 경우도 부모 타입 ITEM 객체로 조회 시
단일 쿼리문으로 위 목적을 위해 빠른 조회가 가능하다.
"즉, 부모 객체 타입의 컬럼을 조회하기 위해서 모든 자식 테이블들에 대해 UNION ALL을 통해 다 뒤져야 한다는 것이다"


2. 자식 테이블 전체를 통합해서 쿼리문 작성 어려움
-> 단점 1과 같은 의미인데 아래와 같은 코드 입력시 JPA는 UNION ALL을 통해 쿼리문을 작성할 수 밖에 없다.
ex)
// 부모 타입 ITEM의 모든 객체 조회 시 모든 테이블에 대해 JPA가 UNION ALL을 작성한다.
List<Item> items =
        entityManager
                .createQuery("select i from Item i", Item.class)
                .getResultList();



상속 관계 전략(김영한 왈)
기본 적으로는 "조인 전략"으로 상속 관계를 DB 모델링한다.
그 위에 조인 전략의 장/단점과 단일 테이블 전략의 장/단점을 고려하여, 트레이드 오프를 생각하여 최종 결정을 하면 된다고 하낟.
